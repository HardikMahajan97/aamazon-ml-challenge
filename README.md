# Business Entity Resolution — Amazon ML Challenge 2026

Given business records from three independent, noisy data sources with no shared
identifiers, decide which records refer to the same real-world business. Source 1 is
the deduplicated reference; for each Source-1 entity the task is to find all matching
Source-2 and Source-3 records — zero, one, or many.

Scored by **macro-averaged F_0.5 per Source-1 entity** — precision weighted 2× over
recall, with correctly-predicted singletons earning a full 1.0.

## Approach

Classical entity resolution, three stages: **retrieve → rerank → classify**.

1. **Normalize** every record once — accent folding, Indic-script romanization,
   canonical legal suffixes (`Pvt Ltd` ≡ `Private Limited`), street abbreviations
   (`Rd` ≡ `Road`), US/Indian state names, and a vowel-stripped consonant *skeleton*
   that realigns transliterated names with their Latin spellings.
2. **Block** with three independent character n-gram TF-IDF indexes per country (name,
   address, name+address), union their top-k lists, and rerank down to 60 candidates
   per entity.
3. **Classify** each candidate pair with LightGBM over ~30 similarity features, then
   apply a `(threshold, margin)` rule tuned directly against the competition metric.

No external data, APIs, or pretrained weights. LightGBM (MIT) is the only model, far
below the challenge's 8B parameter cap.

## Measured results

| Metric | Value |
| --- | --- |
| Blocking pair recall | **91.65%** (15,738 / 17,172 links) |
| Blocking entity recall (all matches found) | 79.40% |
| Reduction ratio | 0.99998548 (from 20.7B in-country pairs) |
| Candidates per Source-1 entity | 60 |
| Peak memory | 6.67 GB |

Measured on a 5,000-entity India sample against the full 4.13M-record reference pool.
The end-to-end F_0.5 is produced by `s3_train.py` on a held-out split.

Test-set scale: 1,732,544 Source-1 entities against 9,969,589 Source-2/3 records.

## Getting started

The dataset is not tracked — it is 2.3GB and every source file exceeds GitHub's 100MB
limit. Place the organiser's files at `student_resource/dataset/{train,test}/` first.

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r student_resource/code/business_entity_resolution/requirements.txt
```

Then pick one of two paths:

- **Notebook** — open **`run_pipeline.ipynb`**. It runs every stage in order with live
  output, checks the instance is big enough before starting, and packages the
  submission zip at the end. Written for a SageMaker notebook instance but works in
  any Jupyter or Colab environment.
- **Shell** — follow **`student_resource/code/business_entity_resolution/RUNBOOK.md`**,
  which gives every command with its measured runtime and peak memory.

Either way, read the guidance before starting: the full run is several hours, and the
blocking stage is deliberately split per country so that a failure costs one country
rather than the whole job.

All paths are overridable by environment variable — `BER_DATA_DIR`, `BER_OUT_DIR` and
`BER_WORK_DIR` — so the dataset and the ~20GB scratch directory do not have to sit
beside the code.

## A note on memory

This pipeline was built and tuned to run inside **16GB of RAM** against 2.3GB of input
and ~104M candidate pairs. That constraint shapes the code throughout — memory-mapped
feature matrices, packed-integer candidate deduplication instead of Python dicts,
copy-on-write forked workers, and per-stage peak-RSS logging. `RUNBOOK.md` documents
which knobs to turn first if memory is tight.
